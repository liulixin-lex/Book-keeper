# 11 旧数据迁移

> 迁移只把旧库作为**数据来源**：按新模型重新生成交易与分录，不沿用旧表结构或旧分录。
> 输入：v1 生产库快照（0.1.8 迁移后版本，SQLite）。数据构成见 §1（具体数量以迁移报告为准，不写入文档）。

## 1. 旧数据构成

| 项 | 情况 |
|---|---|
| 业务记录 | 支出与收入两类，全部为已过账状态 |
| 日期精度 | 日、时间戳、月三种 |
| 金额分量 | 现金、成本、手续费、毛额、净额、额度（UPSTREAM_CREDIT，部分记录） |
| 币种 | CNY 为主；GBP（Stripe）、USD、HKD 少量 |
| 科目 | 8 个（银行存款、应付账款、利润分配、主营业务收入、其他业务收入、主营业务成本、管理费用、财务费用） |
| 分类 | 支出：上游充值、账号购买、云服务、订阅、其他支出；收入：链动收入、云猫收入、Stripe收入、xorpay收入 |
| 往来方 | 上游站点、服务商、交易平台等 |
| 支付账户 | 只有“未指定支付账户” |
| 来源文件 | 少量（只有文件名与路径） |
| 外部 ID | 全部唯一 |
| 元数据中的明细列表 | 兑换明细、日内逐笔、微信订单号、订单列表等 |
| 审计事件 | 全部保留（见 §3） |

## 2. 映射

### 2.1 账套与用户
| 旧 | 新 | 规则 |
|---|---|---|
| workspace | book | 本位币 CNY，时区 Asia/Shanghai，默认科目表（14 号文档 §3） |
| users | users | 邮箱、显示名；argon2id 密码哈希原样保留（v2 可直接验证），其他算法标记为需重置；同邮箱的已有用户（如预先创建的超级管理员）直接复用；角色映射为 owner / accountant / viewer |
| user_sessions、invitations、idempotency_records、backup_* | 不迁移 | |

### 2.2 科目与分类

分类、科目、渠道的完整映射见 **14 号文档 §11.1**。要点：

| 旧 | 新 |
|---|---|
| “未指定支付账户”（银行存款） | 1012.01 资金账户（与新数据相同，不区分微信、支付宝、银行卡） |
| 链动收入 / 云猫收入 / Stripe收入 / xorpay收入 | `sale` → 5001.01 API 额度销售，渠道 = 链动 / 云猫 / Stripe / XorPay |
| 上游充值 | `credit_purchase` → 5401.01 上游额度 |
| 账号购买 | `expense` → 5401.02 账号 |
| 订阅 | `expense` → 5401.03 AI 服务订阅（其中摘要为“手续费”的 → 5603.01 手续费） |
| 云服务 | `expense` → 5401.04 服务器与网络 |
| 其他支出 | 按内容拆分：广告 → 5601.01 广告推广费；公司注册、注册地址 → 5602.01 注册与办公费；XorPay 开户费 → 5603.01 手续费 |
| 手续费分量 | 5603.01 手续费 |

账号、AI 订阅、服务器与网络都直接用于提供 API 服务，与旧系统一样计入主营业务成本，只是拆成了明细科目；“其他支出”从主营业务成本移到对应的期间费用。

### 2.3 往来方、渠道与摘要
- 往来方按 **14 号文档 §7、§11.2** 重命名并分类：上游站点名 = 实际主机名（v1 原主机名转小写，子域不剥；品牌名、俗称如“极光”作为别名，不生成主域名别名；账套主人自己的改名与别名放在本地映射文件里，用 `--mappings` 传入，不写在代码里），服务商用官方品牌名，交易平台用简称，`未知站点` → “未识别站点”（进入待办）；
- 旧 `source_channel`：域名 → 往来方；`legacy:*`、`account_purchase` → 标签 `legacy-channel:<值>`；
- 渠道：收入按旧分类；账号购买按往来方（链动小铺 → 链动、云猫寄售 → 云猫、16888 → 16888）；额度采购按证据（订单列表、`fee_rate`、批次说明）判断链动 / 云猫 / 站内商店，无法判断时为“其他”；订阅与云服务为“官网直付”；
- **摘要重写**：按 14 号文档 §9 的模板重新生成（示例见 §11.3），卡网商品标题按 §9.3 清洗为关键词；含多笔明细的汇总记录写成“{站点} · 额度采购 · {日期} 合计 {笔数} 笔”；旧摘要原样保存在 `metadata.legacy.description`。

### 2.4 交易
| 旧字段 | 新字段 |
|---|---|
| id | `legacy_map`（legacy_table=business_records） |
| accounting_date | effective_date（保持不变） |
| occurred_at、date_precision | occurred_at、date_precision |
| description、note | description（按 14 号文档 §9 重写）、notes（原样） |
| external_id | external_ref |
| business_fingerprint、source_locator、recognition_method 等 | `metadata.legacy.*` |
| metadata 中的 import_batch / reconcile_batch / before_reconcile 等 | `metadata.legacy.*`，批次名另加标签 `legacy-batch:<名称>` |
| status = posted | 迁移后入账 |
| reversed_by_record_id（如有） | 先迁移原交易并入账，再删除（冲销），保持关联 |
| created_by_user_id | created_by_user_id；`created_channel = migration` |

**金额分量 → 模板输入**（全部以旧数据中的实际金额为准，不按手续费规则重算）：

| 旧类型 | 新类型 | 输入 |
|---|---|---|
| 收入 | `sale` | `gross` = 毛额；`fee_actual` = 手续费；结算账户 = 1012.01 资金账户；外币以旧 CNY 金额推得实际汇率（`fx_source = actual`），保证本位币金额不变 |
| 上游充值 | `credit_purchase` | `face` = 成本；`fee_actual` = 手续费；`total` = 现金；`credit_quantity` = 额度分量；付款账户 = 1012.01 |
| 账号购买、订阅、云服务、其他支出 | `expense` | `category` 按 §2.2；`amount` = 成本；`fee_actual` = 手续费（如有）；付款账户 = 1012.01；外币同上 |

校验：现金 = 成本 + 手续费、净额 = 毛额 − 手续费；不成立的记录列入未迁移记录清单，不迁移，待用户处理。

**精度**：旧金额为 1e-8 精度，新系统 CNY 精度为分。原币金额不能整除到币种精度的记录列入未迁移记录；本位币金额按半进位舍入到分，同一交易内的舍入差走尾差行（容差内），报告列出所有被舍入的值与合计差额。

**额度换算约定**：旧数据中“1 CNY = 1 UPSTREAM_CREDIT”的约定 → 商品 `UCR`（kind=credit，scale 4）+ 价格规则 `UCR→CNY = 1`（purpose = nominal_valuation，自 2026-05-01 起）。

### 2.5 证据
- `source_documents`：v1 只记录了上传者本机的 Windows 路径，没有保存文件本身。文件名与 SHA-256 存入 `legacy_archive`，每笔交易的 `metadata.legacy.source_document_id` 保留来源关联；用户提供原件目录时（`--files-dir`），按文件名查找并校验 SHA-256，一致则存入文件库并以 `statement` 用途附加到关联的交易（2026-10-18 快照中 195 笔）；
- 元数据中的明细列表（兑换明细、日内逐笔、微信订单号、订单列表）→ 在来源“历史证据（迁移）”（kind = `manual_list`）下展开为来源记录：日期 + 时间、金额 / 面值、账号标签、订单号等能解析的字段进入标准列，其余进入 `raw`；状态 `booked`，以 `evidence` 角色关联到交易；无法解析的列表原样保留在 `metadata.legacy`。

### 2.6 其他
| 旧 | 新 |
|---|---|
| fx_rates | fx_rates（`rate_e12 → numeric`，保留来源与类型） |
| journal_entries / journal_lines | 不迁移为新分录；全文存入 `legacy_archive` 供对照 |
| audit_events | 存入 `legacy_archive`；新审计链中每个迁移实体有一条 `migration.import` 事件引用旧 ID |
| 0.1.8 移除模块的导出文件 | 只随备份保存，不导入 |

## 3. 流程

| 步骤 | 内容 | 产出 |
|---|---|---|
| 1 冻结 | 停止向 v1 写入（暂停所有导入脚本）；备份 v1 数据库与文件 | v1 最终快照 |
| 2 试迁移 | `bookkeeper legacy-migrate --source v1.db [--files-dir 原件目录]`（默认试迁移，整体回滚） | 迁移报告（Markdown + JSON）：映射与重分类、未迁移记录清单、舍入清单、往来方重命名、核对结果、抽样 |
| 3 确认 | 用户确认报告；分以下精度的处理用 `--subcent round`（默认，舍入并列入清单）或 `anomaly`（不迁移并列入清单） | 确认后的命令参数 |
| 4 正式迁移 | 同一命令加 `--apply`；写入新建账套或 `--book-id` 指定的空账套；以“迁移”身份通过应用层服务写入（同样经过记账校验、审计、哈希链）；核对任何一项不通过则整体回滚 | 新账套 |
| 5 核对 | §4 全部核对项随迁移自动运行，写入报告 | 核对报告 |
| 6 并行 | v1 只读保留 30 天；新数据只进 v2 | |
| 7 切换 | nginx 指向 v2；30 天后停止 v1 容器，归档 v1 数据库（步骤与命令见 15 号文档） | |

迁移命令可重复执行（目标为空账套时），任何一步失败整体回滚。

## 4. 核对项

| 编号 | 核对 | 通过标准 |
|---|---|---|
| V1 | 记录数 | 每条旧记录在 `legacy_map` 中恰好对应一笔交易（未迁移记录清单中的除外，且数量一致） |
| V2 | 按日 × 类型 × 币种的分量合计 | 现金、成本、手续费、毛额、净额与旧金额分量逐项相等（原币精确相等） |
| V3 | 本位币合计 | 收入、成本、费用、手续费、资金净流量与旧分录合计的差额 ≤ 舍入清单合计 |
| V4 | 账本完整性 | 试算平衡为零；`hash_chain`、`entries_balanced`、`balances_cache`、`daily_balances` 检查通过 |
| V5 | 额度数量 | 按往来方的额度数量合计与旧额度分量合计相等 |
| V6 | 证据 | 6 个文件哈希一致；附件关联完整；展开的证据记录数与旧列表元素数一致 |
| V7 | 日期 | 全部 effective_date 与旧 accounting_date 相同；日期精度保留 |
| V8 | 外部 ID | 305 个外部引用全部保留且唯一 |
| V9 | 抽样对照 | 随机 30 条，新旧并排展示（描述、日期、各分量、生成分录） |
| V10 | 报表 | 按月利润表的收入、成本 + 费用、手续费总额与旧系统同口径汇总一致（差额只来自已确认的科目重分类与舍入） |

## 5. 迁移后
- 迁移完成后不立即关闭期间；用户确认核对报告后，可关闭 2026-05 至 2026-09；
- “未识别站点”的交易与渠道为“其他”的额度采购进入待办，可逐步补充；
- v1 数据库、迁移报告、迁移配置文件随备份永久保存。

## 6. 实现与试迁移结果

实现：`bookkeeper/migration/legacy_v1.py` + CLI `legacy-migrate`（迁移 0006 新增 `legacy_map`、`legacy_archive`）。外币记录按旧 CNY 金额推得实际汇率，以交易类型的 `fx_rate` 输入写入，本位币金额与 v1 一致；分以下的金额按 §2.4 舍入并逐条列入舍入清单。

试迁移（本地，PostgreSQL 18）的核对结果：

| 项 | 结果 |
|---|---|
| 记录 | 全部迁移，未迁移 0 |
| 收入 / 成本费用 / 资金净流量 | 与 v1 完全一致 |
| 手续费 | 只有分以下的舍入差；原成本 / 管理费用中的手续费重分类到 5603.01 手续费 |
| 额度数量 | 一致 |
| 证据 | 明细列表绝大部分展开为来源记录，无法解析的保留原文 |
| 原始文件 | v1 未保存文件本身，文件名与哈希已存档 |
| V1–V10 | 全部通过 |

正式迁移需使用冻结后的最新快照重新试迁移（15 号文档 §2–§3）。
