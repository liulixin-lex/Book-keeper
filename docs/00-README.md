## 已确认的决定（2026-10-18）

| # | 问题 | 决定 |
|---|---|---|
| Q1 | 数据库 | 改用 PostgreSQL（采用当前稳定版 18），单机 Docker Compose 托管 |
| Q2 | 上游额度采购口径 | 付款即计入成本；不设预付额度与消耗环节 |
| Q3 | 支出分类 | 按经济实质：上游额度、账号、AI 服务订阅、服务器与网络计入主营业务成本；广告、注册办公、软件工具等计入期间费用（14 号文档 §3–§4） |
| Q4 | 资金账户 | 不区分微信、支付宝、银行卡与平台余额，统一为“资金账户”（多币种） |
| Q5 | 代码与发布 | 新代码在 `bookkeeper-rebuild/v2/`（全新代码），镜像 `book-keeper:2.x`；推送 GitHub 与生产部署前另行确认 |
| — | 分类体系与文案 | 按 14 号文档统一重构科目、分类、类型、渠道、往来方命名、摘要与界面文案；旧数据迁移时一并重写，原文保留 |

## 关键设计决策

| # | 决策 | 理由 | 放弃的方案 |
|---|---|---|---|
| D1 | 业务交易层与会计分录层分离；业务类型由代码定义的构建器生成分录，手工凭证另走受限通道 | 录入简单、分录标准；规则修正后可重过账 [EK1][PY1][ID2][XA-3] | 用户直接录分录；单层交易表；JSON 模板引擎（灵活但复杂，6 种固定类型不需要） |
| D2 | 金额 `bigint` 最小单位；汇率 `numeric`；禁止浮点 | 精确、可在数据库求和 [F1][T9][HS-5] | 浮点；仅定点小数库 |
| D3 | 每张分录同时满足各商品平衡与本位币平衡；跨商品自动生成货币兑换腿 | 杜绝不同币种相加，汇兑损益显式 [T2][HK2][HL2] | 只要求本位币平衡 |
| D4 | 分录只追加：修改与删除在账本中都是冲销与重记，交易编号不变（2026-10-19 起，见 17 号）；数据库触发器与权限强制 | 可审计、防篡改，界面上仍可直接编辑与删除 [F5][T6][EK2] | 直接改写分录；更正另开新交易（已去掉） |
| D5 | 账套级哈希链（分录与审计），每日校验 | 发现数据库层篡改 [PA3][OD8][SQ2] | 仅依赖审计日志 |
| D6 | 科目角色驱动模板与报表；《小企业会计准则》编码；分析口径用维度与往来方，不进科目名称 | 科目表规范且稳定，报表不依赖名称 [DL1][OF1][CN-1] | 按品牌 / 渠道建科目 |
| D7 | 手续费规则独立版本化（比例 + 固定额 + 上下限 + 币种、范围、优先级、估算标记）；扣法由交易类型决定 | 覆盖各渠道与采购场景，可追溯修正 [M2][B1] | 手续费写死在代码中；阶梯计费与内扣 / 加收字段（当前业务用不到） |
| D8 | 导入 = 来源记录（永久保留）+ 去重 + 规则 + 匹配 + 确认 + 入账 | 证据链完整、可重放 [DEG1][BG-1][HS-4] | 直接把文件行写成交易 |
| D9 | 多来源互证用一维最小代价指派（全局最优） | 优于逐条就近贪心 [OR-2][BI-1] | 贪心就近匹配 |
| D10 | 待核对款项 + 统一待办 | 不阻塞入账，未处理事项可量化 [OCA1][ES1][GC4][NM-7] | 未分类数据不入账；结账检查清单（已去掉） |
| D11 | PostgreSQL 18；Python 3.14 | 延迟约束触发器、行锁、多客户端并发写；当前稳定版本 | SQLite |
| D12 | REST 与 MCP 共用应用层；MCP 默认只读、最小权限、写入可先试算（dry_run）、来源标记、变更集撤回 | 外部 AI 可安全读写 [LF1][LF2][MO-1][HM-2][BCC1] | REST 1:1 映射为 MCP；两段式预览（2026-10-19 去掉） |
| D13 | 不内置 AI、审批、订阅模块 | 用户要求；智能能力由外部 AI 经 MCP 接入 | — |
| D14 | 旧数据只作为数据来源重新生成交易，金额以实际值为准 | 数值一致、不引入猜测 | 沿用旧分录；按规则重算历史手续费 |
| D15 | 单一资金账户（多币种），付款即成本 | 用户确认（Q2、Q4）；记账最简 | 按支付工具拆资金科目；预付额度口径 |
| D16 | 外部 AI 是主要操作方式：后端功能完整，接口自描述（类型目录、输入 Schema、示例、报表目录）、宽松引用（编码 / 名称 / ID）、带候选与下一步的错误、批量与预览；前端只求点击少 | 用户要求（2026-10-18） | 只满足前端所需的最小后端 |
