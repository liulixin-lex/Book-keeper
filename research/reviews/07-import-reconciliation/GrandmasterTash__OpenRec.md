# GrandmasterTash/OpenRec

- 分类：07 对账匹配引擎
- 语言 / 许可证 / 最近提交：Rust（+ Lua 规则）/ MIT / 2022-01（停更，但设计完整）
- 审查范围：`docs/{concepts,examples,problems}.md`、`celerity`（匹配引擎）、`jetwash`（清洗）、`steward`（编排）、`examples/*` charters

## 定位

基于文件的对账匹配引擎：每个“控制（Control）”由一个 YAML **charter** 定义，新数据进入收件箱 → 清洗 → 与历史未匹配数据合并 → 分组 → 规则判定 → 匹配的释放、未匹配的留在 outbox。

## 设计要点

- **未匹配数据持续累积**：每次新数据到来，都与之前未匹配的记录一起参与匹配（适合“订单先到、兑换后到”的异步对账）；
- **清洗（Jetwash）**：去空格、日期转 ISO、自动推断列类型（布尔/日期时间/十进制/整数/字符串/UUID），追加记录元数据（来源前缀、文件名、导入时间）；
- **虚拟网格**：多来源记录按列合并为一张网格（如 INV.* 与 PAY.* 两类）；
- **分组 + 约束规则**：`group.by: [REF]` 按键分组，`match_when` 中所有约束为真才算匹配；内置 **nets_to_zero**（两侧金额绝对值之和相等，且两侧都至少有一条）、**带容差净额为零**，以及**自定义 Lua 约束**；派生字段用 Lua 计算（如从描述中提取订单号）；
- **ChangeSet**：对长期未匹配的数据做人工修正（忽略记录、修改字段值），以时间戳命名的 JSON 文件按序处理，形成可追溯的修正日志；
- 匹配作业结果（matched JSON）归档，可审计；外部归并排序支持百万级记录低内存运行。

## 可借鉴

- [OR-1] **未匹配池**：未匹配记录跨批次持续参与匹配。
- [OR-2] 按键分组 + 约束规则（净额为零、容差、自定义表达式）定义“什么算对平”。
- [OR-3] 派生字段（从文本提取键）用安全脚本/表达式实现。
- [OR-4] ChangeSet：对未匹配数据的人工修正（忽略/改值）作为有序、可追溯的指令日志。
- [OR-5] 匹配作业结果归档。

## 不采用 / 风险

- 文件系统作为存储；Lua 引擎对我们不必要（用受限表达式即可）。

## 对新系统的启示

1. 对账域模型：`ReconciliationControl`（定义：参与来源、分组键/候选生成方式、约束规则、容差）→ `ReconciliationRun`（一次运行：输入、匹配组、未匹配）→ `MatchGroup`（成员记录、净额、规则结果）；
2. 未匹配记录持续保留并在新数据到来时重跑；
3. 人工处理未匹配（忽略、改值、手工配对）作为带原因的指令记录。
